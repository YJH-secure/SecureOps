## 1. 프로젝트 목적과 범위

SecureOps는 가상 기업의 Linux 서버를 중앙에서 진단하여 취약점 및 확인 필요 사항을 분류하고, 관리자 승인 후 제한된 보안 조치를 수행하며 재진단 결과를 비교하는 시스템이다.

**목표 흐름:** 대상 등록 → SSH 읽기 전용 정보 수집 → B/C 정책 판정 → D JSON v1.1 취합·집계 → 관리자 승인 → E 백업·조치·재검증·복구 → 보고서·대시보드.

프로젝트 요구 범위는 (1) 서버·네트워크·서비스 기반 구성, (2) 취약점 진단 및 승인 기반 보안 조치 자동화, (3) 결과 통합·시각화/자동 스캐닝, (4) **허가된 격리 실습 환경에서 웹 취약점 SQLi·XSS·파일 업로드 분석 보고서 3건**이다. 웹 분석 보고서 작성은 전체 개발 범위에 포함하되 GNS3 자체가 취약점 테스트를 제공하는 것은 아니다.

**중간발표 우선 구현 경로:** 중앙 관리 서버 → Ubuntu 대상 실제 SSH 읽기 전용 수집 → B 또는 C 결과 1개 생성 → D 최상위 JSON v1.1 보고서 생성 → 팀장 검증 → 증거 제시. 이후 Rocky 확대, 조치/재검증, IDS/WAF, 시각화를 단계적으로 확장한다.

## 2. 기존 VMware 구성과 새 GNS3 목표 구분

### 2-1. 기존 인프라 기준선 (A 담당 구축 보고)

| 서버 ID | 보고된 운영체제 | 기존 VMware VMnet8 NAT IP | 역할 |
| --- | --- | --- | --- |
| `central-mgmt` | Ubuntu Server 24.04.5 LTS | `192.168.10.10` | 중앙 진단·수집·평가·승인 제어 |
| `ubuntu-a` | Ubuntu Desktop 24.04.5 LTS | `192.168.10.20` | Ubuntu 취약점 및 실습 웹 서비스 대상 후보 |
| `rocky-b` | Rocky Linux 9.8 Desktop | `192.168.10.30` | Rocky 취약점 및 DNS/FTP 대상 후보 |

- 기존 네트워크: `192.168.10.0/24`의 **VMnet8 NAT**. 게이트웨이, DHCP 범위, 실제 SSH 포트·계정 및 연결 성공은 담당자 기록과 현장 증거를 재대조한다.
- A 담당자는 3대 VM 구축·SSH 키 인증 관련 검증을 보고했다. **이 사실을 팀장 측 실제 GNS3 연동 성공 또는 통합 검증 완료로 확대 해석하지 않는다.**
- VM의 배포판·GUI 구성은 진단 판정에 영향을 준다. `SVC-01` 등은 서비스 존재 여부와 보안 위반 여부를 구분한다.
- 기존 VMnet8 NAT/VM 스냅샷을 보존한다. IP 변경과 네트워크 어댑터 수정은 인프라 작업 승인 및 복구 준비 후 시행한다.

**근거:** [A 인프라 PR #9](https://github.com/YJH-secure/SecureOps/pull/9) 및 [인프라 문서](https://github.com/YJH-secure/SecureOps/blob/feature/kmw-infrastructure/infrastructure/README.md). 병합 여부와 실측 구성은 진행 시 다시 확인한다.

### 2-2. GNS3 확장 목표 (설계 제안)

VMware는 기존 Linux VM 실행을 담당하고, GNS3는 라우터·스위치 및 연결 토폴로지를 담당한다. 기존 VM 3대의 재사용을 우선 검토하며, 서비스 및 보안 기능은 별도 설치·구성이 필요하다.

```text
                  [Windows 호스트 / VMware Workstation + GNS3]
                                     │
                              [R1: GNS3 라우터]
                     10.10.10.1/24   │   10.10.20.1/24
                             ┌───────┴────────┐
                             │                │
                        [SW-MGMT]        [SW-SERVER]
                             │                ├──────── [ubuntu-a / Web 후보]
                       [central-mgmt]         └──────── [rocky-b / DNS·FTP 후보]

               MGMT 10.10.10.0/24       SERVER 10.10.20.0/24

 IDS: 통과하는 실제 패킷을 관측할 수 있는 미러링/TAP 경로 (미확정)
 WAF: 웹 사용자 요청 → WAF(리버스 프록시) → 승인된 웹 백엔드 (미확정)
```

**주의:** 이 그림은 *논리적 설계*이다. GNS3 프로젝트의 실제 노드별 연결 방식·VMnet 할당·라우터 인터페이스·가상 NIC 개수·트래픽 경로는 설치 환경에서 확인한 뒤 확정한다.

## 3. IP·인터페이스 및 라우팅 설계

### 3-1. GNS3 제안 주소 (기존 IP와 별개)

| 구간 | 네트워크 | R1 제안 인터페이스 IP | 연결 자산/제안 IP |
| --- | --- | --- | --- |
| 관리망 `MGMT-NET` | `10.10.10.0/24` | `10.10.10.1` | `central-mgmt`: `10.10.10.10` |
| 서버망 `SERVER-NET` | `10.10.20.0/24` | `10.10.20.1` | `ubuntu-a`: `10.10.20.20`, `rocky-b`: `10.10.20.30` |

- 주소는 **확정값이 아닌 제안값**이며 호스트 VPN·기존 가상 어댑터·GNS3 기본 서브넷과의 충돌을 점검한다.
- `192.168.10.x`는 **기존 NAT 관리 주소**, `10.10.x.x`는 **신규 GNS3 통신 실험 주소**로 구분한다.
- GNS3용 인터페이스에 임의로 두 번째 기본 게이트웨이를 추가하지 않는다. 실제 기본 게이트웨이와 목적지별 라우트를 결정하고 연결 검증 결과에 따라 조정한다.

### 3-2. 가상 NIC 및 연결 작업 기준

| 대상 | 기존 연결 보존 | GNS3 새 연결 제안 | 필수 확인 |
| --- | --- | --- | --- |
| `central-mgmt` | VMnet8 NAT | 관리망에 연결되는 별도 가상 어댑터 또는 검증된 GNS3 통합 연결 | 인터페이스 이름·IP·라우팅·SSH 출발 주소 |
| `ubuntu-a` | VMnet8 NAT | 서버망에 연결되는 별도 가상 어댑터 또는 검증된 GNS3 통합 연결 | 대상 IP·SSH 포트·서버망 접근 |
| `rocky-b` | VMnet8 NAT | 서버망에 연결되는 별도 가상 어댑터 또는 검증된 GNS3 통합 연결 | 서비스 수신 주소·방화벽·IPv4/IPv6 |

**GNS3/VMware 연결 주의사항 (공식 문서 검토):** GNS3는 VMware VM을 직접 토폴로지에 추가할 수 있으며, GNS3가 연결용 **추가 Host-only VMnet**을 선택·사용할 수 있다. 연결용 Host-only VMnet의 DHCP는 비활성화해야 한다. **기본 VMnet1·VMnet8을 GNS3 전용 연결망이라고 단정하거나 VMnet 번호를 임의 지정하지 않는다.**

기존 VMnet8 NAT 인터페이스가 세 서버 간 우회 경로를 제공할 수 있다. **망 분리와 R1 경유를 검증할 때는 NAT 경로를 통한 직접 통신을 구별**하고, 가상 NIC/라우팅/방화벽의 검증 시나리오를 별도로 작성한다. 원래 접속 경로를 바로 제거하지 않는다.

### 3-3. 최소 통신 정책 (설계 초안)

| 출발 | 목적 | 목적/원칙 |
| --- | --- | --- |
| 중앙 관리 서버 | 허가된 대상 Ubuntu/Rocky | SSH 원격 수집, 실제 포트·출발지 허용 목록 검증 |
| 진단 대상 서버 | 중앙 관리 서버 | 필요한 응답 트래픽과 명시 승인된 결과 전송만 허용 |
| 테스트 사용자/프록시 | 웹 서비스 또는 WAF | 승인된 실습 요청만; WAF 우회 경로 존재 여부 확인 |
| 관리자 조치 계층 | 승인된 대상 서버 | 진단 계정과 분리, 별도 승인 및 감사 기록 |
| 그 외 관리망↔서버망 | 해당 없음 | 기본 제한 방향을 설계하고 실제 방화벽 정책으로 검증 |

**검수:** R1 인터페이스 및 대상 IP 확인 → 관리망/서버망 통신 확인 → 정해진 SSH 동작 확인 → 우회 경로 및 방화벽 규칙 확인 → 증거 수집. `ping`만 성공했다고 SSH·IDS·망 분리가 검증된 것은 아니다.

## 4. 소프트웨어·서비스·보안 기능 배치

| 기능 | 우선 배치/구현 후보 | 추가 자원 | 현재 판단 |
| --- | --- | --- | --- |
| SecureOps 중앙 프로그램 | `central-mgmt`의 Python/SSH | 기존 VM 1대 | 개발 진행, 실서버 E2E 미검증 |
| Linux 진단 대상 | `ubuntu-a`, `rocky-b` | 기존 VM 2대 | A 구축 보고, GNS3 연결 미검증 |
| DNS | `rocky-b`의 DNS 서비스 후보 | 우선 기존 VM 활용 | 설치·정책·동작 검증 필요 |
| FTP | `rocky-b`의 `vsftpd` 후보 | 우선 기존 VM 활용 | 수신 포트 관측과 허용 접근은 별개; 최종 정책 미확정 |
| Web / 격리 실습 | `ubuntu-a` 또는 별도 실습 컨테이너 후보 | 기존 VM 또는 추가 컨테이너 | 웹 분석용 환경·범위 미확정 |
| IDS | 트래픽 관측이 가능한 구간의 IDS 센서 후보 | 별도 센서 VM/컨테이너 가능 | TAP·미러링·실제 가시성 미검증 |
| WAF | Web 앞단 리버스 프록시 후보 | 별도 VM 또는 컨테이너 가능 | 트래픽이 반드시 WAF를 경유하는지 검증 필요 |
| GNS3 라우터·스위치 | R1, SW-MGMT, SW-SERVER | GNS3 노드; 종류에 따라 VM 자원 필요 | 장비 유형·이미지·라이선스 미확정 |
| GNS3 VM | QEMU/특정 어플라이언스 필요 시 | 별도 지원 VM 가능 | 필요 여부 및 호스트 자원 미확정 |

**VM 수 계산:** 처음부터 무조건 7~8대의 VMware VM이 필요한 것은 아니다. **기존 Linux VM 3대가 출발점**이고, IDS·WAF·GNS3 VM은 구현 방식과 PC 사양에 따라 추가될 수 있다. R1과 스위치는 반드시 별도의 VMware Linux VM으로 세지 않는다.

보안 기능을 `설치됨`이라고 표현하려면 구성 화면뿐 아니라 **동작과 경로의 증거**가 필요하다. IDS는 패킷이 실제 센서까지 복제·전달되는지 확인하고, WAF는 정상·차단 시나리오에서 웹 서버로 가는 요청이 프록시를 경유하는지 확인한다.

## 5. SSH Agentless 수집과 기능 경계

### 5-1. 계층별 책임

```text
인벤토리(target_id, OS, 접속 대상)
            │
            ▼
common/ssh_client.py  ── 읽기 전용 원격 수집 / 오류 반환
            │
            ▼
checks/account, checks/system ── 정책 기준에 따라 개별 검사 판정
            │
            ▼
core ── 결과 정규화 / 최상위 JSON v1.1 생성 / 상태 집계·저장
            │
            ▼
팀장 Integration Validator ── 독립 규격·중복·전후 결과 확인
            │
            ▼
remediation ── 관리자 승인 / 백업 / 허용 조치 / 재진단 / 복구
```

기존 공통 수집기 `common/ssh_client.py`는 **프로토타입 구현 및 SSH MOCK 단위 테스트 성공 보고**가 있다. 실제 Ubuntu/Rocky VM의 SSH 연결과 권한 검증이 완료됐다는 뜻은 아니다.

### 5-2. 공통 수집 인터페이스 (현재 프로토타입 기준)

```python
from common.ssh_client import run_readonly, SSHCollectionError

collected = run_readonly(
    target_id="ubuntu-a",
    host="192.168.10.20",  # 기존 NAT 환경의 설계 주소 예시; 실측 후 적용
    username="secureops-scan",
    operation="os_kernel",
)
# collected: 수집 결과. JSON v1.1의 개별 진단 결과와 다름.
```

- `operation`은 승인된 **읽기 전용 허용 목록**으로 제한한다. 임의 셸 문자열을 정책 파일에서 받아 실행하는 방법은 이 단계에서 사용하지 않는다.
- SSH 호스트 키 확인(`StrictHostKeyChecking=yes`), 비대화형 인증(`BatchMode=yes`) 및 접속 시간 제한을 유지한다. 최초 신뢰 등록은 담당자가 별도로 지문 검증한다.
- SSH 실패·권한 오류·수집 실패는 해당 진단의 `error` 근거로 전달하고 임의로 `pass`/`vulnerable` 처리하지 않는다.
- **실제 실행 모델은 결정 대기:** (A) 중앙에서 원격 값을 수집해 중앙 B/C 코드로 판정, (B) 대상에서 B/C 모듈을 일시 실행하고 결과를 전송. 어느 모델을 사용할지와 함수 호출/반환, 배포·권한·로그 처리를 B/C/D/A와 함께 확정한다.
- SSH 진단 계정과 E 조치 계정은 분리한다. 진단용 함수가 조치 명령을 실행하지 않도록 유지한다.

## 6. 공통 JSON v1.1 계약 — 확정

**기준:** [공통 JSON v1.1 결과 계약](json-result-contract-v1.1.md), [JSON Schema](json-result-schema-v1.1.schema.json), [MOCK 샘플](../../tests/fixtures/sample-result-v1.1-MOCK.json).

| 범위 | 필수 필드 |
| --- | --- |
| 스캔 보고서 (D 생성) | `schema_version="1.1"`, `scan_id`, `target_id`, `os`, `scanned_at`, `results` |
| 검사 항목 (B/C 생성) | `check_id`, `status`, `severity`, `evidence`, `recommendation` |

- `target_id`는 `ubuntu-a`, `rocky-b`처럼 **IP와 독립적인 논리 ID**이다. `server_id`, `os_type` 등 구 필드를 최종 출력에 혼용하지 않는다.
- `scanned_at`은 타임존이 있는 스캔 완료 시각, `checked_at`은 개별 항목의 선택 필드다.
- `status`는 정확히 `pass`, `vulnerable`, `error`, `not_applicable`, `needs_review` 중 하나다.
- `severity`는 소문자 `critical`, `high`, `medium`, `low`만 허용한다. 현재 승인된 8개 항목에 `critical`을 임의 배정하지 않는다.
- `evidence`는 **필수 문자열**, 세부 수집 근거는 선택적 `details` 객체에 기록한다. 인증 정보·비밀번호·개인키·토큰은 저장하지 않는다.
- `recommendation`은 필수 문자열이며 **실행 가능한 조치 명령으로 자동 해석하지 않는다.**
- 이행률: `pass / (pass + vulnerable) × 100`. 분모가 0이면 `N/A`; `error`, `not_applicable`, `needs_review`는 별도 건수이며 분모에서 제외한다.
- 동일 보고서 내 중복 `check_id`를 금지한다. 재진단 때는 새 `scan_id`를 생성하고 스캔 이력을 구분한다.
- 레거시 입력 변환은 D의 명시적 어댑터 범위에서만 허용하며, 상충 값은 임의 선택하지 않는다.

**현재 테스트:** 팀장 브랜치에서 SSH MOCK 5개와 JSON 계약 8개의 **로컬 자동 테스트 13/13 통과**를 사용자가 실행 화면으로 확인했다. 이는 MOCK/Schema 검증이며 실제 SSH·B/C/D/E E2E의 완료 증거는 아니다. `requirements-dev.txt`에 `jsonschema[format]>=4.23,<5`를 기록하여 날짜 형식 검사 의존성을 관리한다.

## 7. 취약점 점검 정책 v1.1 및 서비스별 판단

**기준:** [취약점 점검 기준표 v1.1](../security-policy/vulnerability-checklist-v1.1.md). JSON 스키마 버전과 점검 정책 버전은 **서로 독립적으로 관리**한다.

| 담당 | 정책 점검 ID | 상태 |
| --- | --- | --- |
| B · 최종욱 | SSH-01, SSH-02, ACC-01, ACC-02 | 기준표 존재; 코드 구현·승인·통합 검증 별도 |
| C · 김서후 | FILE-01, SVC-01, FW-01, LOG-01 | 기준표 존재; OS별 세부 기준 및 통합 검증 별도 |

- `pass`는 승인 기준을 충족했다는 **진단 판정**이지, Python 단위 테스트의 `OK`가 아니다.
- `needs_review`는 정책 미승인·예외 등 수동 검토 대기; `error`는 수집·파싱·권한 등 진단 실패. 둘 다 자동 조치 대상으로 삼지 않는다.
- `FILE-01`: `/etc/passwd`·`/etc/shadow` 권한·그룹·ACL 및 Ubuntu/Rocky별 허용 값의 최종 승인 전에는 `needs_review`를 유지한다.
- `SVC-01`: Desktop 기본 서비스나 열린 수신 소켓을 전부 취약으로 단정하지 않는다. 서비스 승인 목록, 사용 목적, 바인딩, 호스트 방화벽, 출발지 접근 가능성을 함께 확인한다.
- DNS·FTP·웹 서버를 실습 목적으로 추가했다면 해당 서버의 서비스 허용 목록과 판정 정책을 **먼저 변경 승인**해야 한다.
- `SSH-01`: `PermitRootLogin`과 `Match`/`Include` 조건에 따른 최종 유효 설정 판정 및 예외 승인 상태를 기록한다.

## 8. 관리자 승인·조치·재검증·복구 원칙

1. `vulnerable` 결과라도 **점검 정책 승인**, 자산·조치 항목·관리자 승인·조치 허용 목록을 확인한 뒤에만 E가 조치를 수행한다.
2. 조치 전에 설정 파일/서비스 상태 백업, VMware 스냅샷 또는 되돌림 수단, 관리자 접속 유지 경로를 확인한다.
3. 진단 계정과 조치 계정의 권한을 구분하고 조치 이력을 남긴다.
4. 조치 후 **새 `scan_id`**로 동일 항목을 재진단하고 `target_id + check_id`로 전후를 대응시킨다.
5. 조치 실패·관리자 접근 손실·서비스 회귀 발생 시 승인된 복구 절차를 수행하고 결과를 기록한다.
6. `error`, `not_applicable`, `needs_review`는 조치 후보에서 자동 제외한다. 특히 승인되지 않은 `/etc/shadow` 권한·PAM 변경을 자동화하지 않는다.
