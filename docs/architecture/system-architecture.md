# SecureOps 시스템 아키텍처 설계서

**문서 버전:** v0.2 (인프라 구성안 반영)  
**작성 담당:** 양지혁  
**관련 Issue:** ARCH-01 (#2)  
**상태:** 팀 검토용 설계안 — 구축 완료/통신 검증 완료를 의미하지 않음  
**변경일:** 2026-11-05

## 1. 설계 목적과 범위

SecureOps는 가상의 중소기업 A사가 운영하는 Linux 서버의 취약점을 중앙에서 자동으로 진단하고, 관리자 승인 기반 보안 조치와 재검증을 수행하기 위한 시스템이다.

핵심 흐름은 **원격 진단 → 결과 수집(JSON) → 위험도 평가 → 관리자 승인 → 조치 → 재검증**이다. Ubuntu에서 1차 통합을 검증하고 Rocky Linux 호환성으로 확장한다.

## 2. 서버 구성 (김민우 인프라 구성안 반영)

| 구분 | 운영체제/형태 | 예정 IP | 역할 |
| --- | --- | --- | --- |
| 중앙 관리 서버 | Ubuntu Server 24.04 LTS | `192.168.10.10` | 진단 작업 실행, SSH 연결 관리, 결과 통합/평가, 승인·조치 제어 |
| 진단 대상 A | Ubuntu 24.04 LTS Desktop | `192.168.10.20` | 1차 Linux 취약점 진단 및 재검증 |
| 진단 대상 B | Rocky Linux 9.8 Desktop | `192.168.10.30` | 다른 배포판의 점검 및 조치 호환성 검증 |

**출처와 검증 수준:** 2026-11-05 김민우 담당자가 팀 채널에 공유한 구축 계획을 반영했다. 실제 설치 완료, IP 적용 상태, SSH 통신 성공 여부 및 VM 사양은 **아직 증거 확인 전**이며 담당자의 실행 결과로 검증해야 한다.

### Desktop 사용에 관한 판단

Ubuntu Desktop과 Rocky Desktop도 Linux 점검 대상이 될 수 있다. 다만 GUI/추가 패키지 때문에 Server 버전과 기본 서비스·설정이 달라져 **SVC-01 등 검사 결과에 차이**가 생길 수 있다. 점검 로직은 GUI 조작에 의존하지 않아야 하며, 서비스의 부재를 임의로 `pass`나 `vulnerable`로 처리하지 않는다. `not_applicable`과 `error` 처리 기준은 점검 기준표와 공통 JSON 규격에 맞춰 협의한다.

## 3. 가상 네트워크 구성안

- 가상화: VMware Workstation
- 네트워크: **VMnet8 NAT**, 계획 대역 `192.168.10.0/24`
- 관리 서버 및 대상 서버 2대가 같은 VMnet8에 연결된다는 구성안
- 중앙 관리 서버에서 대상 A/B로 **SSH(TCP 22, 기본 설정 기준)** 접속하는 방식을 우선 검토
- VMnet8 가상 네트워크 설정, 게이트웨이, DHCP 할당 범위, IP 중복 여부와 실제 SSH 포트는 구축 담당자가 확인

> 이 절의 IP/네트워크 값은 **팀 공유 설계값**이며, 실제 연결/접속 성공을 단정하지 않는다. 변경 시 이 문서와 인프라 문서를 함께 갱신한다.

## 4. SSH 기반 Agentless 진단 아키텍처 (설계안)

중앙 관리 서버가 등록된 대상 서버에 SSH로 인증하고, 대상의 Linux 설정을 **읽기 전용**으로 확인한 뒤 결과를 수집하는 방식이다. 진단 대상 서버에 SecureOps 전용 상주 에이전트를 배포하지 않는 구성을 우선 검토한다.

### 논리적 구성

```text
[SecureOps 중앙 관리 서버 | Ubuntu Server | 192.168.10.10]
  ├─ 진단 실행/스케줄 관리 (추후 구현)
  ├─ SSH 원격 수집 계층 (구현 방식/담당 확정 필요)
  ├─ checks/account + checks/system 진단 로직
  ├─ core 결과 취합·위험도 평가
  └─ remediation 승인 확인·조치·재검증
            │
            ├─ SSH → [Target A: Ubuntu Desktop | 192.168.10.20]
            └─ SSH → [Target B: Rocky Desktop | 192.168.10.30]
```

**중요:** 위 그림은 최종 동작 목표를 설명한 논리도이다. Python 모듈을 원격에서 직접 실행할지, 중앙에서 원격 수집한 값을 분석할지는 아직 확정되지 않았다. 팀원들이 각자 SSH 접속·권한 코드까지 중복 구현하지 않도록 원격 수집 계층의 인터페이스를 먼저 합의한다.

## 5. 처리 흐름

1. 중앙 관리 서버에서 등록된 대상과 진단 항목 선택
2. SSH 인증 및 원격 점검에 필요한 최소 권한 확인
3. 계정·SSH/파일·서비스·방화벽·로그 설정의 **읽기 전용** 진단
4. 진단 결과를 공통 구조의 JSON 데이터로 취합
5. `pass` / `vulnerable` / `error` / `not_applicable` 구분 및 위험도 평가
6. 관리자 승인 전에는 **실제 설정 변경 금지**
7. 승인된 항목만 사전 백업·복구 계획 확인 후 보안 조치
8. 동일 항목 재진단 및 조치 전후 비교·이력 기록

## 6. 공통 데이터 계약 및 서버 식별자

공통 결과 형식은 [JSON 결과 규격 v1.0 검토 초안](json-result-contract-v1.md) 참고.

- 서버 구분 필드: **`target_id`** (현재 초안 명칭; `server_id`와 혼용하지 않도록 팀 합의 필요)
- 대상 A 논리 식별자: `ubuntu-a`
- 대상 B 논리 식별자: `rocky-b`
- `target_id`는 SSH hostname이나 IP 문자열 그 자체가 아닌 **안정적인 논리 식별자**로 사용
- 인증 정보, 비밀키, 비밀번호를 JSON 결과나 GitHub에 업로드하지 않음
- 진단 결과의 `evidence`에는 판정 근거만 기록하고 비밀값은 제외

## 7. 팀원별 개발 영역

| 담당자 | GitHub 폴더 | 주요 책임 |
| --- | --- | --- |
| 양지혁 | `docs/architecture/`, `docs/security-policy/` | 아키텍처, 점검·위험도 정책, 데이터 계약, 통합 검증 |
| 김민우 | `infrastructure/` | VMware/서버/네트워크 구축, 접속 및 스냅샷 검증 |
| 최종욱 | `checks/account/` | SSH·계정/인증 점검 및 결과 객체 생성 |
| 김서후 | `checks/system/` | 파일 권한·서비스·방화벽·로그 점검 및 결과 객체 생성 |
| 조효민 | `core/` | JSON 수집·검증·집계·위험도 평가 |
| 박태준 | `remediation/` | 관리자 승인 확인·백업·조치·재검증/복구 설계 |

코드는 각자 지정된 이니셜 포함 `feature/` 브랜치에 커밋하고, 변경 사항은 PR로 검토한 다음 `main`에 반영한다.

## 8. 보안 설계 원칙

- 진단 기능과 시스템 설정 변경 기능을 분리한다.
- 관리 서버와 진단 서버 간 SSH 접근은 승인된 테스트 계정 및 필요한 최소 권한으로 제한한다.
- 관리자 승인 여부, 조치 대상, 조치 성공/실패 이력을 추적한다.
- SSH·방화벽·PAM 설정 변경 전 복구 경로와 관리자 접근 유지 수단을 확인한다.
- Rocky Linux에서 `authselect`가 관리하는 PAM 파일은 무작정 직접 수정하지 않으며 관리 방식과 복구 절차를 먼저 확인한다.
- VMware 스냅샷은 서버 식별자와 작업 시점을 포함해 관리한다. 예: `ubuntu-a-pre-remediation-261105` (명명 규칙 제안)
- 허가된 실습용 서버에서만 진단·설정 변경을 수행하고, 실습 인증 정보나 개인키는 커밋하지 않는다.
