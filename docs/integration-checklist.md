## 0. 판정 언어와 공통 계약

- **완료(실환경·개별):** 실제 VM에서 해당 대상/해당 항목을 실행하고 입력·출력·저장 재조회 증거를 확보했다는 뜻. 2개 대상 **개별 성공 ≠ 동시 다중대상 자동화 완료**.
- **완료(오프라인/MOCK):** 기존 JSON·fixture·가상 상태/회귀 테스트 근거. **운영 서버 실제 수집·조치 완료 아님**.
- **부분:** 정확히 증명된 하위 범위만 완료. **대기:** 승인·기능·환경·실측 증거가 없는 상태.
- 결과 JSON v1.2: `schema_version/scan_id/target_id/os/scanned_at/results`, 결과별 `check_id/status/evidence/recommendation/cvss` 필수, `details` 보존, v1.2 개별 `severity` 금지. 상태 `pass/vulnerable/error/not_applicable/needs_review`; CVSS v3.1 `scored/pending/not_applicable`, 미평가 점수 `null`.
- 이행률 `pass / (pass + vulnerable)`; `error/not_applicable/needs_review`를 임의로 정상 또는 분모에 넣지 않는다. 분모 0이면 N/A.
- 본 문서 승인 원칙: 팀원간 기술 협의·담당 브랜치 개발은 자율, **공통 정책·인터페이스 변경/서버·sudo·네트워크 설정/실제 배포/main 병합은 팀장 최종 승인 후 적용**. 착수와 최종 반영은 분리한다.

## 3. SSH-01 기존 E2E 재현 기준 (기준선 보존)

- 기존 환경: 관리 Ubuntu `192.168.10.10` → Ubuntu `192.168.10.20` / Rocky `192.168.10.30`. 11/16 **서버별 독립 실행** 성공.
- 정상 진단 흐름: SSH 접속·호스트키 확인 → 승인 수집기 무인자 실행 허용 및 금지 명령 거부 → B SSH-01 판정 → JSON v1.2 필수 필드·CVSS `pending`·`null` 확인 → D ReportStore 저장/`scan_id` 재조회·동등성 확인.
- 결과가 `vulnerable`이어도 **실행 검증 PASS**가 될 수 있다(두 서버 `PermitRootLogin without-password`). 이 결과로 보안 조치 성공 또는 서버 취약점 개선 완료를 주장하지 않는다.
- GNS3 목표: 중앙 IP `10.40.0.10`은 별도 네트워크의 **예정 값**. 원본 `ssh01_context`/`ROOT_CONTEXT`/`targets.json`을 변경하지 않는다. B·D·A가 제안한 신규 환경용 문맥과 실제 `sshd -T -C` 값·호스트키를 대조하고 팀장 승인 후 복제본에만 적용한다.
- 11/16 증거를 11/20 신규 검증으로 날짜 바꾸거나, 원본을 취득하지 않은 D 독립 SHA 대조 완료로 표기하면 안 된다.

## 4. 통합 STOP 규칙·증거 무결성

1. 신규 명령/권한/변경이 승인 범위를 넘으면 **즉시 중단**, 원본 결과와 오류를 보존하고 팀장에게 승인 요청한다. sudoers·원본 VM·방화벽 정책을 임의 수정하지 않는다.
2. 대상·OS·실행자·KST 시각·기준 커밋/PR SHA·명령과 인자·권한·종료 코드·입력 출처(실VM/ZIP/fixture/MOCK)·원시 JSON 해시·보고서 저장/재조회·오류/롤백·정책 승인 상태를 구분한다.
3. 권한 부족이나 journal 가시성 제한은 `error`; LOG 원인 보강 #34는 `error` 유지이며 신규 운영 검증 전 Draft. 불명확한 정책은 `needs_review`. 확인되지 않은 값은 `pass`나 CVSS 점수로 치환하지 않는다.
4. 변경 전 백업/복구 확인, 기존 서비스·관리 SSH 접속 유지, 허용된 작업의 정확한 범위, 중단 시 복구 담당·조건을 마련하지 못한 설정 변경은 진행하지 않는다.
5. main PR은 **코드 검토·회귀·실환경 영향·의존성·팀장 승인**이 완료된 뒤에만 병합한다. 11/16 SSH-01 E2E 성공으로 #24/#26 자동 병합하지 않는다.

#### 2. 당장 이어질 실행 순서와 실패 시 기준

1. **팀장 + A(11/12~13)**: `ssh -G` 별칭·접속 user/port/key 파일명, 대상 `sshd -T -C`의 `addr/host/user` 문맥, 기존 `secureops-scan` sudoers와 별도 SSH01 sudoers 설치 여부 확인. 설정 변경 전 별도 승인.
2. **팀장(11/13~16)**: PR #24 코드·README, #26 실행기(두 파일) 및 main 기반 로컬 180·C163 회귀 증거 보존. 안전한 승인 후 새 VM 한 대 SSH01 수집→B→D 원시 결과/저장·재조회.
3. **D(11/16)**: 실제 JSON의 `target_id/os/scanned_at/scan_id`, 상태/CVSS null, 보고서 재조회 원본 검증. **MOCK 데이터를 실측 데이터로 대체 기록 금지.**
4. **C(11/16 이후)**: 대상 VM에서 C 로컬 CLI를 승인된 읽기 전용 방식으로 실행하고 수집 결과를 중앙에 전달. FILE/LOG 원격 metadata 및 허가된 명령 마이그레이션은 추가 설계.
5. **E(11/17)**: 승인·백업·조치·재진단·롤백의 MOCK 화면과 D/E 이력 연결 증거, 운영 조치와 구분된 발표 자료.
6. **실서버 연동 실패 시:** 실패한 정확한 단계·권한·종료 코드·호스트·시각·원인과 실패 로그를 남기고, MOCK 시연에는 `MOCK` 표시. 근거 없이 완료 체크 금지.
