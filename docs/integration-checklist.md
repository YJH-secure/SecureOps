# SecureOps 통합 검증 체크리스트 (팀장 관리)

> 작성: 2026-11-09 / 상태: 실행 계획. **아직 검증하지 않은 항목을 완료로 표시하지 않는다.** 정책: [JSON v1.1 계약](architecture/json-result-contract-v1.1.md) · [점검 기준표 v1.1](security-policy/vulnerability-checklist-v1.1.md) · [현황표](project-status.md).

## 0. 공통 원칙

- 대상은 허가된 실습 환경 한정. 진단은 읽기 전용, 실제 조치는 별도 관리자 승인·백업·복구·접속 유지 검증 후 시행.
- 서버 식별자 `central-mgmt`, `ubuntu-a`, `rocky-b`; 실측 IP/OS는 A 인프라 표와 실행 시점 대조. 실제 GNS3 구현 여부는 별도 증거가 필요.
- 비밀번호, 개인키, 인증 토큰과 민감한 로그는 저장소에 넣지 않는다.
- 결과 `pass`는 승인된 정책 충족 의미, **테스트 통과**와 구별한다. 정책 보류 `needs_review`나 검사 오류 `error`를 조치 완료로 표시하지 않는다.

## 2. 각 테스트의 필수 증거

- 테스트 날짜/담당, 실행 OS/서버 자산 ID, 브랜치/커밋 SHA
- 실행 명령/입력 데이터 분류(MOCK·fixture·실측), 예상값, 실제값, PASS/FAIL 판정
- 민감정보를 제거한 결과 JSON·터미널 캡처·오류 로그 및 트러블슈팅
- 정책 및 버전, 승인자, 재검증 시 새 scan_id
- 결과 PR 링크와 최종 검토/병합 여부

## 3. 검사 자동화 구현 경계

- **B/C**: 각 담당 진단 및 자체 단위 테스트.
- **D**: 운영용 결과 정규화·집계·저장.
- **E**: 승인된 조치 실행, 백업, 복구 및 재진단.
- **팀장 Integration Validator**: 독립적인 계약·모듈 연동·조치 전후 결과 테스트 및 증거 보고. B/C/D/E 운영 로직 중복 개발 금지.

## 4. 중간발표 최소 시나리오

`central-mgmt` → SSH로 대상 1대에 읽기 전용 진단 실행 → 결과 1건 수신 → D가 최상위 JSON v1.1 생성 → 팀장 Validator의 규격/상태 검증 → 결과·실패 사항 보고.

단위 MOCK 테스트만 통과했으면 '모의 검증', 실제 SSH 실행과 D 연동까지 완료한 경우에만 '통합 검증 완료'라고 표기한다.
