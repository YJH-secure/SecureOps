## 2. 확정된 공통 개발 기준

- 결과 JSON 계약 **v1.1** 사용: 최상위 `schema_version`, `scan_id`, `target_id`, `os`, `scanned_at`, `results`; 개별 진단은 `check_id`, `status`, `severity`, `evidence`, `recommendation` 필수.
- 상태: `pass`, `vulnerable`, `error`, `not_applicable`, `needs_review`; 세부 근거는 `details`로 보존.
- 이행률은 `pass / (pass + vulnerable) × 100`; `needs_review`, `error`, `not_applicable`은 별도 집계.
- 진단 정책 기준표 v1.1은 계약 스키마와 **별개**. OS별 파일 권한, SSH 조건, 서비스·방화벽 허용 범위가 미승인이라면 `needs_review`를 유지하며 임의 `pass` 처리 금지.
- GitHub 협업: 기능 브랜치 → PR → 팀장 검토·재현 테스트 → 승인 시 `main` 병합.

## 3. 미해결 항목과 위험

1. **GNS3와 실제 Linux VM 연결**: VPCS 간 ping은 성공했으나 중앙 서버·Ubuntu/Rocky 진단 대상과 네트워크 토폴로지 실제 연결 증거는 없음. KVM 이슈는 보류.
2. **중앙 원격 진단 인터페이스**: 팀장 SSH 실행 결과(성공/종료 코드/표준 출력/오류/대상 ID)를 B/C, D와 연결해야 함.
3. **정책 승인**: FILE-01 `/etc/passwd`·`/etc/shadow` 권한/ACL, SVC-01 서비스·소켓/IPv4·IPv6/출발지, FW-01 정책 근거를 자산별 확정해야 함.
4. **D/E 이력 연계**: 진단 JSON v1.1과 조치 실행 이력은 분리. `execution_id`, `before_scan_id`, `after_report`, `outcome`, `rollback`의 저장·재조회, 실패/거부/건너뜀 구분 필요.
5. **실제 보안 조치**: MOCK 성공으로 서버 실제 조치를 승인할 수 없음. 관리자 승인·백업·롤백·접속 영향 검증 전에는 읽기 전용으로 제한.
6. **발표 산출물**: 중간발표 2026-11-18, 최종 제출 2026-12-01 18:00, 최종발표 2026-12-02. PDF 결과 보고서·발표자료, 5~10분/100MB 이하 MP4 시연 영상, README/GitHub 링크와 웹 취약점 분석 보고서 3건 준비 필요.
