# ADR-001: 정책 승인·검증 범위 및 프로젝트 기록 관리

- 날짜: 2026-11-09
- 상태: **문서화 제안 / PR 리뷰 대기** (기존 확정 JSON 계약 자체는 변경하지 않음)
- 책임: 팀장(아키텍처·정책·통합 검증)

## 배경

다수 팀원이 서로 다른 브랜치에서 SSH/FILE/SVC 진단, 결과 집계, 조치 기능을 병렬 개발한다. MOCK 통과와 실제 운영 기준 승인, 개별 진단과 중앙 원격 실행 통합, VMware 실측과 GNS3 목표를 혼동하면 오탐·잘못된 조치·포트폴리오 과장 위험이 있다.

## 결정/제안

1. JSON 결과 계약은 [확정 v1.1 문서](../architecture/json-result-contract-v1.1.md)를 단일 기술 기준으로 사용한다. 스키마를 임의 변경하지 않는다.
2. OS별 세부 보안 기준/허용 서비스/서버 역할은 담당자가 근거와 실측으로 **후보**를 제안하고 팀장이 별도 검토 후 승인한다. 미승인 기준을 승인된 것으로 표시하지 않는다.
3. 정책과 결과의 5개 상태를 구분한다. **확인된 정책 위반 → vulnerable; 수집 실패 → error; 수집됐지만 승인 불명확 → needs_review**. 다중 원인이 발생하면 `details`에 모두 보존한다.
4. SVC-01의 활성 전체 서비스는 현황 증거로 보존하고, **서비스·수신 소켓·방화벽 접근성**은 각각의 근거로 평가한다. 목록 밖 서비스가 취약인지 여부는 사전에 승인한 allowlist/deny-by-default 규칙과 대상 자산 역할을 기준으로 판단한다. 이 세부 기준은 **승인 대기**다.
5. FILE-01의 passwd/shadow 소유자·그룹·권한 및 ACL/심볼릭 링크의 OS별 예외는 팀장 승인 전까지 **후보**이며, 실제 조치 자동 실행 금지.
6. 진단 담당 B/C와 결과 집계 D, 조치 E, 팀장 독립 검증기를 분리한다. 변경은 기능 브랜치 PR과 테스트 증거를 통해 검토하고 `main`에 직접 수정하지 않는다.
7. 대화에서 합의한 내용과 GitHub 실제 코드가 불일치하면 일단 상태를 **재확인 필요**로 기록하고 파일/PR/테스트 근거를 대조한다.

## 대안·판단

- 모든 활성 서비스를 자동 취약 처리: Desktop 기본 서비스 특성 및 미확정 정책 때문에 오탐 가능 → 승인된 정책 없이 채택하지 않음.
- 와일드카드(0.0.0.0/::) 바인딩만 보고 외부 노출 확정: FW/NAT 접근성 정보 부족 → 채택하지 않음.
- 전체 작업을 팀장 브랜치에 직접 합치기: 다른 팀원 미완료 작업과 충돌 위험 → PR 검증 절차 유지.

## 영향 및 후속

- **A**: 서버 역할/망/방화벽 IPv4·IPv6 허용 범위와 실제 도달성 증거.
- **C**: SVC-01/FILE-01 세부 후보안·회귀 테스트와 `needs_review` 증거 보존.
- **D**: 개별 결과에서 최상위 JSON v1.1 생성 및 `error/needs_review` 집계 분리.
- **E**: 미승인 정책 및 오류 상태를 자동 조치 대상에서 제외.
- **팀장**: [진행 현황](../project-status.md)과 [통합 검증](../integration-checklist.md)을 확인하여 최종 정책·병합 판단 기록.

## 개인 기여도 기록 원칙

정책 판단·아키텍처·팀장 직접 작성 테스트/검증 도구는 팀장 기여로 기록한다. B/C/D/E 담당자의 구현 코드를 팀장 단독 구현으로 기재하지 않는다. 실제 완료 증거가 없으면 성과로 주장하지 않는다.
